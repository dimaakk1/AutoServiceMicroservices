# Тестові дані для прогнозування ремонту

Команда створює окремий набір синтетичних даних: категорії, послуги з деталями й постачальниками, клієнтів, майстрів, автомобілі, завершені замовлення та їхні позиції. Для кожного замовлення окремо зберігається пробіг на дату ремонту в `OrdersMlSeed.dbo.MlSeedVehicleSnapshots`. Фактичний і плановий час завершення можна використати для визначення затримки.

## Поточні тестові бази AppHost

1. Запусти або перезапусти `AppHostt.AppHost` у профілі Development.
2. Дочекайся запуску сервісів каталогу, користувачів, автомобілів і замовлень.
3. В Aspire Dashboard відкрий **Resources**, знайди **ml-seed** і вибери **Start** у меню ресурсу.
4. У **Console logs** для **ml-seed** перевір повідомлення `Seed batch saved.`

Ресурс запускається лише вручну. AppHost сам передає підключення до своїх `OrdersDb`, `CatalogDb`, `UsersDb` і `VehiclesDb`. Сідер додає партію, повторно використовує наявні категорії й послуги з відповідними назвами та не оновлює чи видаляє наявні записи. Повторний запуск не дублює партію. Для AppHost знімки пробігу лежать у `OrdersDb.dbo.MlSeedVehicleSnapshots`. Якщо після оновлення сторінки в адмінці ще видно старий список, дочекайся оновлення кешу.

## Експорт CSV для навчання

Для AppHost після запуску оновленої версії відкрий **Resources → ml-export → Start**. Експорт читає `OrdersDb` і записує `artifacts/ml/repair-orders.csv` відносно кореня репозиторію. Шлях і кількість записів з’являться в логах ресурсу. Якщо партію вже додано, запускати `ml-seed` повторно не потрібно.

Для окремого тестового Docker Compose після запису партії використай:

```powershell
dotnet run --project tools/MlSeed -- --export
```

Один рядок відповідає одному замовленню, записи впорядковані за часом запису. `service_ids` містить JSON-масив ID послуг, `service_count` — їхню сумарну кількість, а `planned_budget_minutes` — час від слота запису до погодженого завершення. `duration_minutes` і `delayed` — цільові колонки; фактичні часові мітки до CSV не потрапляють. `order_id` залишено для звірки, а не як ознаку моделі. Імена клієнтів, VIN та контакти не експортуються. Якщо бракує замовлення або воно має некоректні дані, команда поверне помилку і не замінить попередній CSV.

## Окремий тестовий Docker Compose

Попередній перегляд без підключення до SQL:

```powershell
dotnet run --project tools/MlSeed
```

Запис в окремі тестові бази з кореня репозиторію (PowerShell 7):

```powershell
$env:ML_SEED_SQL_PASSWORD = Read-Host 'Пароль для окремого SQL Server' -MaskInput
# Необов’язково: щоб створені клієнти й майстри могли входити у сайт.
$env:ML_SEED_DEMO_PASSWORD = Read-Host 'Пароль для демо-акаунтів' -MaskInput
docker compose -p autoservice-ml -f docker-compose.yml -f docker-compose.ml-seed.yml up -d --wait sqlserver
dotnet run --project tools/MlSeed -- --apply
```

Вибери пароль SQL, що відповідає правилам SQL Server. Уникай крапки з комою та лапок у ньому, бо цей пароль також використовують рядки підключення демо-стеку. Параметри сідера: `--count 1000 --seed 42 --end-date 2026-11-01`. З однаковими параметрами генератор відтворює той самий набір; контрольна сума відображається у виводі. Повторний запис з тими самими параметрами перевіряє дані й не створює дублікатів. Для іншої партії потрібен новий ізольований SQL-том.

Для перегляду в адмінці зупини звичайний стек, якщо він займає порти застосунку, і запусти тестовий із тими самими параметрами Compose:

```powershell
docker compose -p autoservice-ml -f docker-compose.yml -f docker-compose.ml-seed.yml up -d frontend
```

SQL тестового стека доступний лише локально на порту `11433`; бази мають суфікс `MlSeed`, а том відділений від основного. Для демо-акаунтів використовуються адреси `ml-user-001@autoservice.test` і `ml-mechanic-001@autoservice.test` тощо. Без `ML_SEED_DEMO_PASSWORD` профілі існують для зв’язків із замовленнями, але пароля для входу не мають. Сідер не створює платежі, не викликає пошту, Telegram чи зовнішній VIN-сервіс.
